# INTERFACES.md — the contract between backend, Flutter and native

**STATUS: PROPOSED. Not signed off. No implementation may start against it yet.**

> ⚠ **THE RULE (`SPEC.md` §3):** once this file is signed off, **any change to anything
> in it STOPS work and goes back for sign-off.** That applies to route paths, field
> names, field types, enum values, status codes and token lifetimes. Adding a field is
> a change. Renaming a field is a change. Widening an enum is a change.

Everything here is `application/json` over HTTPS. All timestamps are **RFC 3339 UTC with
a `Z` suffix**, generated by the **server** clock (`SPEC.md` §4.3). All money is an
**integer**; see §6 for the unit, which is the single easiest thing to get wrong.

---

## 1. Error envelope — every non-2xx response, without exception

```json
{ "error": { "code": "DEVICE_CONFLICT", "message": "human readable, safe to display" } }
```

`code` is a closed enum. The client switches on `code` and **never** parses `message`.

| `code` | HTTP | Meaning | What the client does |
|---|---|---|---|
| `OTP_INVALID` | 401 | Wrong PIN | Show retry, decrement attempts |
| `OTP_EXPIRED` | 401 | PIN TTL elapsed, or `otpToken` unknown | Send them back to phone entry |
| `OTP_ATTEMPTS_EXHAUSTED` | 429 | Infobip `attemptsRemaining` hit 0 | Back to phone entry, new send required |
| `OTP_SEND_FAILED` | 502 | Infobip returned `MESSAGE_NOT_SENT` or unreachable | "Could not send the code", offer retry |
| `RATE_LIMITED` | 429 | Our own limiter (§5.5) | Show `retryAfterSeconds` |
| `DEVICE_CONFLICT` | 409 | Account already active on another device | The "already active elsewhere" screen + Force Login |
| `SUBSCRIPTION_EXPIRED` | 402 | Valid session, lapsed subscription | Membership/renewal screen |
| `NO_SUBSCRIPTION` | 402 | Account exists, never subscribed | Membership screen |
| `UNAUTHORIZED` | 401 | Missing/invalid/expired access token | Silent refresh, then re-auth |
| `SESSION_REVOKED` | 401 | Refresh token revoked, or reuse detected | Full logout, clear local state |
| `DEVICE_REVOKED` | 401 | This device was revoked by a Force Login elsewhere | Full logout, explain why |
| `PAYMENT_FAILED` | 402 | Gateway reported failure | Failure screen, offer retry |
| `PAYMENT_NOT_VERIFIED` | 402 | Callback arrived, ZarinPal did not confirm | Failure screen |
| `VALIDATION_ERROR` | 400 | Malformed request | Bug — log, generic message |
| `INTERNAL` | 500 | Anything else | Generic message |

**`402` is deliberate and load-bearing.** `SPEC.md` §5.4 requires that an expired
subscription is *not* a generic 401. `401` means "who are you"; `402` means "we know
exactly who you are and you must pay".

## 2. Token lifetimes and transport

| Token | Lifetime | Storage | Transport |
|---|---|---|---|
| Access | **15 minutes** | client memory + secure storage | `Authorization: Bearer <jwt>` |
| Refresh | **60 days**, rotated on every use | secure storage only | request body of `/auth/refresh` only |
| `otpToken` | **15 minutes**, single use | client memory only | request body of `/auth/verify-otp` |
| Entitlement blob | see §5 | secure storage | never sent to the server |

Refresh tokens are stored **hashed** server-side (SHA-256, no reversible form). Rotation
is strict: using a refresh token invalidates it and issues a new one. **Presenting an
already-rotated refresh token is reuse** ⇒ the entire token family is revoked and the
response is `SESSION_REVOKED`.

Access-token claims: `sub` (user id), `did` (device id), `exp`, `iat`, `jti`.
**`did` is in the access token on purpose** so device authorisation is checked without a
database round trip on every request.

## 3. Routes

### `POST /auth/send-otp`
```json
→ { "phone": "09121234567" }
← 200 { "otpToken": "opaque-…", "expiresAt": "2026-08-30T19:15:00Z", "attemptsAllowed": 10 }
```
Phone is normalised to E.164 **before** anything else (`SPEC.md` §4.8): `09xxxxxxxxx` →
`+989xxxxxxxxx`. `+989…`, `989…`, `00989…` and `09…` all resolve to one account.
**The response never contains Infobip's `pinId`** — it is held server-side against
`otpToken` (`ARCHITECTURE.md` §8.10). The response is **identical whether or not an
account exists**, so this endpoint is not an account-enumeration oracle.

### `POST /auth/verify-otp`
```json
→ { "otpToken": "opaque-…", "pin": "123456",
    "device": { "deviceId": "uuid-v4", "platform": "android|ios",
                "deviceName": "Pixel 7", "appVersion": "1.0.0+1" } }
```
Four possible successes, discriminated by `next`:
```json
← 200 { "next": "SIGNUP_REQUIRED",  "signupToken": "…", "expiresAt": "…" }
← 200 { "next": "PAYMENT_REQUIRED", "signupToken": "…", "expiresAt": "…" }
← 200 { "next": "SESSION",          "session": { …§4… } }
← 409 { "error": { "code": "DEVICE_CONFLICT",
                   "activeDevice": { "deviceName": "iPhone 13", "lastSeen": "…" } } }
```
`DEVICE_CONFLICT` carries `deviceName` and `lastSeen` **and nothing else** — enough to
let a person recognise their own other phone, not enough to profile it.
`signupToken` authorises `/payment/create` **only**. It is not a session.

### `POST /auth/force-login`
```json
→ { "otpToken": "opaque-…", "device": { …as above… } }
← 200 { "session": { …§4… }, "revokedDevice": { "deviceName": "iPhone 13" } }
```
Requires a **fresh, unused** `otpToken` — a Force Login can never be replayed from a
token already spent on `/auth/verify-otp`. Revokes the prior device and **every** refresh
token in its family, atomically, then registers the new device.

### `POST /auth/login`
Convenience alias for an existing account with an already-registered `deviceId`; same
response shapes as `verify-otp`'s `SESSION` / `DEVICE_CONFLICT`. Requires a valid
refresh token, not an OTP.

### `POST /auth/refresh`
```json
→ { "refreshToken": "…" }
← 200 { "session": { …§4… } }
← 401 SESSION_REVOKED | DEVICE_REVOKED
```

### `POST /auth/logout`
```json
→ { "refreshToken": "…" }
← 204
```
Revokes the refresh-token family and the device session **server-side first**; the client
clears local state only after a 204. Idempotent.

### `GET /subscription/status`
```json
← 200 { "status": "ACTIVE|EXPIRED|NONE",
        "expiresAt": "2026-09-29T12:00:00Z",
        "serverTime": "2026-08-30T19:00:00Z",
        "plan": { "code": "monthly", "priceToman": 400000, "days": 30 },
        "entitlement": { …§5… } }
```
`serverTime` is returned **so the client never has to trust its own clock**
(`SPEC.md` §4.3).

### `POST /payment/create`
```json
→ { "planCode": "monthly" }        // Authorization: Bearer <access|signup token>
← 200 { "paymentId": "…", "redirectUrl": "https://payment.zarinpal.com/pg/StartPay/<authority>",
        "amount": 4000000, "currencyUnit": "IRR" }
```

### `GET|POST /payment/callback`
Consumed by **ZarinPal**, not by the app. Query `?Authority=…&Status=OK|NOK`.
Backend verifies with ZarinPal, then **302-redirects into the app** via the deep link in
§7. It never trusts `Status` (`SPEC.md` §4.2).

### `POST /analytics/event` — *pending the §8.9 decision*
```json
→ { "name": "otp_requested", "at": "2026-08-30T19:00:00Z" }
← 204
```
Closed enum of eight names, `SPEC.md` §6.1. **No properties, no device fingerprint, no
third-party SDK.** Blocked on sign-off; see the questions at the end.

```json
  "user": { "id": "…", "phone": "+989121234567" },
  "device": { "deviceId": "…", "registeredAt": "…" },
  "subscription": { …the GET /subscription/status body… } }
```

## 5. The entitlement blob — the offline contract

```json
{ "payload": { "userId": "…", "deviceId": "…",
               "expiresAt": "2026-09-29T12:00:00Z",
               "issuedAt": "2026-08-30T19:00:00Z",
               "graceDays": 14, "version": 1 },
  "signature": "base64(Ed25519(canonical_json(payload)))" }
```

- Signed by the **backend's Ed25519 private key**. The app ships only the **public** key.
  A client that can forge this can forge anything, so the private key never leaves the server.
- The client accepts the blob only if **all** hold: signature verifies · `deviceId`
  matches this install · `now < expiresAt` · `now < issuedAt + graceDays`.
- **`issuedAt + graceDays` is what bounds offline use.** Pulling the device clock backwards
  cannot extend it, because moving the clock back also fails `now >= issuedAt`.
- Refreshed on every successful `/subscription/status`.
- **Evaluated at session start only, never mid-session** (`ARCHITECTURE.md` §8.8) — a
  co-driver's numbers must never blank at speed. ⚠ **This is a proposal awaiting sign-off.**

## 6. Money — the unit, stated once, in one place

**ZarinPal's default amount unit is RIAL** (`ARCHITECTURE.md` §8.6, from ZarinPal's own docs).

```
plan price            = 400,000 Toman        ← what the user is told
amount sent to gateway = 4,000,000 Rial      ← ×10
```

- `plans.price_toman` (integer Toman) is what the UI renders.
- `payments.amount` + `payments.currency_unit` store **exactly what was sent to the
  gateway**, unit included. Never store a bare number.
- `verify.json` must be called with the **same** amount as `request.json`.
- ZarinPal `code` **100** = verified now · **101** = *already verified*. **101 is a
  success that must NOT activate a second subscription.** Together with
  `UNIQUE (gateway, authority)` this is the duplicate-callback defence (`SPEC.md` §7.17).

## 7. The native contract — deep link back from the gateway

None of this exists today (`ARCHITECTURE.md` §8.4). Both platforms need it.

| | Value |
|---|---|
| Scheme | `irallymeter` |
| Return URL | `irallymeter://payment/callback?paymentId=<id>&result=success\|failed` |
| Android | `VIEW` + `BROWSABLE` intent-filter on `.MainActivity`. It is `launchMode="singleTop"`, so the callback lands in **`onNewIntent`**, not a fresh activity. |
| iOS | `CFBundleURLTypes` in `Info.plist`. `AppDelegate` currently overrides neither `application(_:open:options:)` nor `continue userActivity` and uses `didInitializeImplicitFlutterEngine` — that is where the plumbing goes. |

**The deep link carries no entitlement and no payment status the client may trust.** It
is a *wake-up signal only*: on receipt the app calls `GET /subscription/status` and
believes only that (`SPEC.md` §4.2).
